# Experiment 4: Joins, Subqueries, Set Operations, and EXPLAIN Execution Plans

## Aim
Using the Employee–Department–Project relational schema, construct and execute SQL queries utilizing `INNER JOIN`, `LEFT JOIN`, self-join, 3-way join, correlated subqueries, `EXISTS`, and simulated `INTERSECT` and `EXCEPT` operations. Analyze and compare query execution plans using MySQL's `EXPLAIN` utility.

---

## Concepts Demonstrated

### 1. Join Varieties
- **`INNER JOIN`**: Returns records with matching values in both joined tables.
- **`LEFT JOIN`**: Returns all records from the left table (`Department`) and matched records from the right table (`Employee`), with `NULL` where no match exists.
- **Self-Join**: Joins the `Employee` table to itself using aliases (`E1` and `E2`) with inequality condition `E1.emp_id < E2.emp_id` to pair colleagues in the same department without redundant reflexive pairs or permutations.
- **Three-Table Join**: Traverses foreign-key chains connecting `Employee` to both `Project` and `Department`.

### 2. Subqueries & Predicates
- **Correlated Subquery**: Evaluates once for each candidate row processed by the outer query (`WHERE E.salary > (SELECT AVG(E2.salary) ... WHERE E2.dept_id = E.dept_id)`).
- **`EXISTS` Subquery**: Semi-join operator that halts scanning as soon as the first matching project record is found for an employee's department.

### 3. Set Operations (Simulated vs Native)
- **Simulated `INTERSECT`**: Solved via multiple intersecting subquery predicates:
  ```sql
  WHERE emp_id IN (SELECT emp_id FROM Employee WHERE city = 'Delhi')
    AND emp_id IN (SELECT emp_id FROM Employee WHERE salary > 60000);
  ```
- **Simulated `EXCEPT`**: Solved via negation filtering:
  ```sql
  WHERE emp_id NOT IN (SELECT emp_id FROM Employee WHERE city = 'Delhi');
  ```
  *Note on MySQL Compatibility*: While modern MySQL versions (8.0.31+) introduce native `INTERSECT` and `EXCEPT` keywords, the simulated patterns using `IN` / `NOT IN` guaranteed universal portability across earlier MySQL releases while testing relational subquery filtering.

### 4. Query Plan Analysis with `EXPLAIN`
Using `EXPLAIN` provides the query execution plan generated by MySQL's optimizer, exposing:
- `select_type`: `SIMPLE`, `PRIMARY`, `SUBQUERY`, or `DEPENDENT SUBQUERY`.
- `type`: Access type (`const`, `eq_ref`, `ref`, `range`, `index`, `ALL`).
- `possible_keys` and `key`: The indexes considered versus chosen.
- `rows`: Estimated number of rows MySQL expects to inspect.
- `Extra`: Additional processing details such as `Using where`, `Using temporary`, or `Using filesort`.

## Expected Outputs & Query Insights

1. **Self-Join**: Generates non-duplicate pairs of employees working in the same department (e.g., Alice & Bob in HR, Alice & Charlie in HR).
2. **Correlated Subquery**: Identifies top department earners such as Ian in IT (Salary: 72,000 vs IT Avg) and Eva in Finance.
3. **Simulated Intersect**: Returns high earners residing in Delhi (e.g., Ian, who is in Delhi and earns 72,000).
4. **`EXPLAIN` Comparison**:
   - The `INNER JOIN` utilizes foreign key indexes on `dept_id` for efficient `ref` or `eq_ref` lookup.
   - The correlated subquery exhibits `DEPENDENT SUBQUERY` in the explain plan, highlighting the per-row inner aggregation cost.
